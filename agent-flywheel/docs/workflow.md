# Workflow

This workflow is inspired by Agent Flywheel's core loop, but adapted for a Codex-first internal factory that values code quality over uncontrolled parallelism. The factory builds and improves the future study-agent product and any later OSS devkit; it is not itself the public product/devkit.

## 1. Spec First

Do not start from implementation. Start from a feature spec that answers:

- What user workflow changes?
- What is in scope and out of scope?
- What domain objects are affected?
- What public API or UI contract changes?
- What prompt behavior changes?
- What failure cases matter?
- How will the change be verified?

Use `feature-spec-architect` to create the spec.

For a full implementation lane, start the run with `scripts/flywheel-runner.py intake`, collect context with `context`, create the spec scaffold with `spec`, and run `validate --stage spec` before turning the plan into task state. The runner writes a manifest under `docs/flywheel-runs/<run-id>/` so later phases do not depend on chat memory.

## 2. Convert Spec to Task Beads

A task bead is a self-contained unit of work. It should be small enough for one worker to complete without redesigning the feature.

Good beads are not one-line todos. They include context, acceptance criteria, dependencies, and verification.

Use `implementation-orchestrator` to create task beads. When `br` is active, write beads directly there instead of duplicating them in a separate task format. When `bv` is active, use it to select the next ready work from the dependency graph.

For agent-generated task graphs, prefer `scripts/flywheel-runner.py beads --beads-json <tasks.json> --create-br-beads`. This keeps markdown task files and `br` state linked from the same run manifest. Run `validate --stage dispatch` after briefs are generated and before worker dispatch. Dispatch requires a context pack and a non-Draft spec.

## 3. Generate Worker Profiles

Do not assign work from a fixed taxonomy of permanent worker types. Worker specialization should be generated by the orchestrator from the current spec, task graph, repo state, and quality constraints.

Use `worker-profile-factory` when repeated or specialized work appears. It should produce reusable profiles that define:

- responsibility and scope boundaries;
- context to read before acting;
- preferred tools and skills;
- coordination expectations;
- verification and handoff requirements.

Profiles can be reused across beads, but they should stay tied to observed needs. Update or retire stale profiles.

When using the runner, a task bead declares the need with `create <profile-id>` or `reuse <profile-id>` in its `Worker Profile` section. Run `scripts/flywheel-runner.py profiles` before `briefs`; validation fails if a required profile is missing.

## 4. Assign Worker Briefs

Worker briefs are task-specific instructions derived from the task bead and, when available, a reusable worker profile. They should constrain the worker:

- package or files to inspect;
- behavior to implement;
- tests to add;
- boundaries to avoid;
- expected output.

Use `scripts/flywheel-runner.py briefs` to generate consistent worker brief files after task beads are materialized. Then use `scripts/flywheel-runner.py dispatch --ready-only` to generate durable `multi_agent_v1.spawn_agent` packets for the orchestrator when `br` beads are linked. The sequenced `run` command applies ready-only dispatch automatically for linked `br` beads.

## 5. Implement Locally

Workers implement only their assigned task. If a worker discovers the task is underspecified, the correct move is to update the task bead or spec, not to invent architecture silently.

If Agent Mail is active, use the bead ID as the message thread ID and reserve likely file paths before editing. Do not create a competing coordination mechanism when Agent Mail fits.

If a worker needs a real decision, create it with `scripts/flywheel-runner.py decision-request` instead of burying the question in chat. Reversible implementation details should proceed with documented assumptions; product, architecture, safety, dependency, and release decisions should wait for an answer. Open blocking decision requests fail validation until resolved.

## 6. Review Before Merge

Run `code-quality-governor` after implementation. The review should prioritize:

- correctness bugs;
- API drift;
- missing tests;
- prompt/eval regressions;
- source-grounding failures;
- avoidable coupling;
- dependency creep.

After each worker finishes, record its completion with `scripts/flywheel-runner.py worker-report --task <task-id> ...`. Worker dispatch proves work was assigned; worker reports prove that assigned work completed or surfaced a blocker.

Use `scripts/flywheel-runner.py review --command '<verification command>' --semantic-verdict approved` to capture verification command outputs and the final governor verdict. A review with no commands, failed commands, or no approved semantic verdict does not satisfy final status or publication gates.

Prepare publication with `scripts/flywheel-runner.py git-lane` and `scripts/flywheel-runner.py pr-lane`. Both are inspect-first by default, require `--execute` for mutation, and block execution on failed final gates unless `--override-gates` is explicit.

## 7. Capture Durable Decisions

Write an ADR when a change affects architecture, provider choices, persistence model, prompt policy, or evaluation philosophy.

## 8. Optimize The Factory

Run `workflow-optimizer` at the end of meaningful sessions, after repeated agent friction, or after a review finds a pattern that should become reusable guidance. Use `scripts/flywheel-runner.py optimize` or `templates/session-end-checklist.md` so the step is not forgotten. The optimizer should propose concrete updates to AGENTS.md, skills, templates, worker profiles, prompts, or quality gates.

## Minimal Tooling

Until a real task graph tool is adopted, use:

```text
docs/specs/
docs/tasks/
docs/worker-profiles/
docs/worker-briefs/
docs/decision-requests/
docs/reviews/
docs/adr/
```

When this becomes too manual, adopt `br` and `bv`. When concurrent agents start colliding, adopt Agent Mail.

## Optional Oversight

Dashboard or mobile oversight can come later for monitoring active beads, answering blockers, and reviewing status while away from the workstation. It is optional infrastructure, not a current first-class requirement. The workflow should remain complete with Codex, specs, beads, generated worker profiles, review gates, and direct reuse of `br`/`bv`/Agent Mail when those tools are warranted.
