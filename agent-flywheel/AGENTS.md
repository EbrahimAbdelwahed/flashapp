# AGENTS.md

Instructions for AI coding agents working in this repository.

## Mission

Maintain the internal study-agent development flywheel. This directory is the private factory for building the future study-agent product and any later public devkit; it is not itself the OSS product/devkit. Optimize for correctness, maintainability, and durable velocity. The user can move fast only if the workflow and produced code stay clean enough for many future agents to understand.

## Core Rules

- Start from the relevant spec, task bead, or ADR before editing code.
- Keep changes small, scoped, and reviewable.
- Do not introduce dependencies without an explicit reason in the spec or task bead.
- Do not put LLM calls in UI components.
- Do not hardcode API keys or provider assumptions.
- Keep prompts versioned and testable.
- Keep generated study outputs traceable to sources and prompt versions.
- Prefer adapters around external frameworks so the domain model stays portable.
- Do not run tests, lint, type checks, builds, validators, or smoke suites
  locally. Push the scoped branch and use GitHub Actions as the sole
  verification environment.

## Artifact Ladder

Work should move through these artifacts:

```text
raw idea
-> feature spec
-> task beads
-> reusable worker profile when needed
-> worker brief
-> code change
-> review report
-> ADR or docs update when needed
```

If implementation reveals missing structure, step back to the spec or task bead instead of improvising architecture in code.

## Plan Space

Use plan space for:

- product behavior;
- architecture choices;
- public API contracts;
- domain model changes;
- prompt policy;
- evaluation strategy;
- risk and failure handling.

Plans live in `docs/specs/` or `docs/adr/`.

## Task Space

Use task space for scoped implementation units. A good task bead includes:

- context;
- exact work;
- files or packages likely involved;
- dependencies;
- acceptance criteria;
- verification;
- out-of-scope boundaries.

Task beads live in `docs/tasks/` unless an external tracker is adopted.

## Worker-Profile Space

Do not maintain a fixed taxonomy of permanent worker roles. Worker specialization should be generated by the orchestrator from the approved spec, task graph, repository constraints, and observed implementation patterns.

Use `worker-profile-factory` to create reusable profiles when a task graph needs specialization. A good worker profile includes:

- responsibility and decision boundaries;
- required context to read first;
- tools and skills to prefer;
- files or packages normally in scope;
- quality checks and handoff expectations;
- coordination rules for `br`, `bv`, and Agent Mail when those tools are active.

Profiles are reusable assets, but they should remain grounded in real work. Retire or revise profiles that become stale instead of forcing future tasks into an old taxonomy.

## Code Space

Implementation agents should:

- read the task bead and worker brief;
- inspect existing code before editing;
- modify only the scoped surface;
- add or update tests for changed behavior;
- update docs when public behavior changes;
- report verification results.

## Multi-Agent Coordination

When multiple agents work at once:

- each worker should claim a task bead before editing;
- do not edit files reserved by another active worker;
- leave progress notes in the task bead or coordination thread;
- avoid broad refactors unless explicitly assigned;
- never revert unrelated work.

Prefer direct reuse of Agent Flywheel coordination tools once concurrency justifies them:

- use `br` for bead storage and status;
- use `bv` for graph-aware ready-task selection;
- use Agent Mail with task bead IDs as thread IDs and reserved file paths as advisory locks.

Markdown artifacts are acceptable before those tools are adopted, but do not invent a parallel coordination protocol when `br`, `bv`, or Agent Mail already fit the need.

## Oversight UI

A dashboard or mobile oversight surface is optional and later-stage. It may help the user inspect active work or answer blockers away from the workstation, but it is not a current first-class requirement. Keep the core flywheel operable through specs, beads, worker profiles, Codex, `br`/`bv`, and Agent Mail before depending on a UI.

## Quality Bar

Before a change is considered done:

- The GitHub Actions workflow for the exact commit must be green. Local test
  output is not accepted as completion evidence.
- TypeScript must pass strict type checks.
- Unit tests must cover domain logic.
- Prompt changes must include fixtures or eval notes.
- RAG changes must preserve citation and source traceability.
- UI changes must include loading, empty, and error states.
- Public APIs must be documented.
- Dependency additions must be justified.

## CI-Only Verification

All executable verification belongs in `.github/workflows/ci.yml`. This
includes pytest, Ruff, mypy, package build, clean-wheel import, validators,
scaffold checks, and deterministic runner smoke tests.

Agents may inspect files and diffs locally, but must not execute verification
commands before or after editing. To verify a change:

1. commit the scoped change;
2. push its branch to GitHub;
3. wait for the workflow attached to that exact commit;
4. fix failures from GitHub logs and repeat.

`scripts/run-core-tools-smoke.sh` is an environment diagnostic for separately
installed `br`, `bv`, and Agent Mail binaries. It is not a repository test and
must not be presented as CI evidence unless those tools are later pinned and
installed by the workflow.

## Study-Agent Domain Rules

- The platform is source-first: important answers and generated study objects should know their sources.
- Course profiles should influence prompt behavior through structured policy, not ad hoc prompt branches.
- Flashcards are study objects with lifecycle, provenance, audit status, and scheduling state.
- Spaced repetition is first-class product behavior, not just Anki export.
- Anki compatibility is useful, but the product should not depend on Anki as its scheduling engine.
- RAG may use frameworks such as LlamaIndex, but framework objects must not leak into core domain types.

## Recommended Skills

- Use `feature-spec-architect` for rough ideas and feature shaping.
- Use `implementation-orchestrator` for decomposing approved specs into tasks.
- Use `worker-profile-factory` when the orchestrator identifies reusable specialization needs.
- Use `study-prompt-system-designer` for course profiles, prompt registries, and evals.
- Use `study-rag-architect` for retrieval, indexing, citation, and RAG framework choices.
- Use `code-quality-governor` before merge or handoff.
- Use `workflow-optimizer` at the end of meaningful sessions to identify improvements to AGENTS.md, skills, templates, worker profiles, prompts, and quality gates.

Write user-facing explanations in clear, concise language without reducing technical precision. Prefer concrete wording over unexplained jargon. Use established domain terminology when it is the most precise choice, and briefly define it when the intended audience may not know it. Preserve material evidence, constraints, tradeoffs, caveats, and uncertainty. Do not rewrite code, identifiers, commands, quoted text, or prescribed formats merely to satisfy this style rule.
